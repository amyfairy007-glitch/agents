# JSP → React 迁移项目逐行代码治理对比提示词

你现在要对一个已经完成初步 JSP → React 迁移、界面表现基本正常的 AI 生成项目进行“逐文件、逐段、逐行”的代码治理与标准仓库对齐。

本任务不是第三轮规范总结，也不是重新生成一套抽象 Guide，而是直接以两个成熟标准仓库的真实代码为事实依据，对当前 AI 项目的实际代码做收敛治理。

目标是：在不破坏当前业务行为和页面表现的前提下，尽可能让当前 AI 项目的代码组织、公共组件使用、调用链、表单、校验、请求、状态处理、命名、文件职责和开发流程，与两个标准仓库的真实实现保持一致。

---

## 一、输入对象

执行前先明确并记录以下 4 个输入：

1. 【当前 AI 项目仓库】
2. 【标准仓库 A】
3. 【标准仓库 B】
4. 【本次目标 market + journey】

如果目标 market 或 journey 已由当前任务上下文明确，不要重复询问。

默认边界：

- 只治理当前 market + `core`
- 只治理当前目标 journey
- 不默认读取其他 market
- 不默认修改其他 journey
- 只有发现真实跨 journey / 跨 market 依赖时才扩展，并先记录原因

---

## 二、核心原则

### 1. 标准仓库真实代码优先

所有“应该怎么写”的判断必须能回到标准仓库真实代码。

禁止仅依据：

- 通用 React 最佳实践
- AI 自己偏好的架构
- 网络文章
- 当前 AI 项目已经形成的自有写法
- 之前生成但没有成熟仓库代码证据支持的抽象规则

如果标准仓库已有明确模式，优先让 AI 项目向标准仓库靠拢，而不是反过来用 AI 项目现有模式解释合理性。

### 2. 两个标准仓库共同模式优先级最高

如果两个标准仓库在同类场景采用一致模式，则视为高可信标准。

如果两个标准仓库写法不同：

- 不要擅自选一个
- 分析差异产生的真实原因
- 判断是版本差异、业务差异、market 差异、journey 差异、历史遗留，还是两种均被允许的实现
- 证据不足时标记“待人工确认”

### 3. 不追求“文本一模一样”

目标是实现方式、职责分层和流程一致，而不是机械复制代码。

必须区分：

- 业务必然差异
- market/localchange 差异
- journey 专属差异
- 依赖/API 版本导致的合理差异
- AI 自造且无标准仓库依据的差异

### 4. 优先消除 AI 自造层

重点识别 AI 项目中标准仓库不存在或不需要的：

- wrapper
- adapter
- helper
- hook
- component
- utils
- 状态层
- API 封装
- 表单封装
- validation 封装
- request 参数组装
- 常量层
- 转换层
- 重复抽象

任何 AI 自造层都必须回答：

> 标准仓库中是否存在同职责实现？

如果不存在，必须进一步判断它是否真的有必要。

如果只是 AI 为了迁移方便生成的中间层，并且移除后能直接回到标准仓库方式，则优先删除或收敛。

### 5. 保持业务行为不变

治理期间默认不改变：

- 页面展示结果
- 字段含义
- 按钮行为
- API 业务参数语义
- 路由行为
- market 特有逻辑
- localchange 业务差异
- 用户可见流程

如果标准化必须改变业务行为，停止该项修改并标记“需要人工确认”。

---

## 三、不要再做什么

本轮禁止：

1. 不要重新做一轮全仓库迁移文档治理。
2. 不要再生成一套大而全的候选规范。
3. 不要先写几十页 Guide 再开始看代码。
4. 不要因为“代码能运行”就认为已经对齐。
5. 不要因为 AI 项目多个文件都使用同一模式，就把该模式视为正确标准。
6. 不要为了代码更现代、更优雅而偏离标准仓库。
7. 不要进行与当前 journey 无关的大范围重构。
8. 不要顺手升级依赖、框架、组件库或构建体系。
9. 不要清理与当前治理目标无关的历史代码。
10. 不要一次性重写整个 journey。

## 四、第一阶段：建立当前 journey 的真实代码地图

先只读，不修改代码。

完整读取当前目标 journey 相关文件和直接依赖，建立真实调用链。

至少覆盖：

- route / 页面入口
- page/container
- 子组件
- config
- constants
- strings
- validation
- buildRequest / request 参数组装
- API/service
- response 处理
- hooks
- utils
- common component
- loading
- error
- modal
- table
- pagination
- mock / stub
- dev / sit 环境处理
- localchange

输出当前 journey 调用链，例如：

```text
route
  ↓
page
  ↓
初始化请求
  ↓
状态初始化
  ↓
字段组件
  ↓
validation
  ↓
submit
  ↓
buildRequest
  ↓
API
  ↓
response/error
  ↓
跳转/刷新/提示
```

必须使用真实文件路径和真实函数名。

## 五、第二阶段：在两个标准仓库中寻找对应实现

不要泛泛扫描整个标准仓库。

根据当前 journey 中出现的具体场景逐项寻找对应实现。

例如当前 journey 有：

- Input
- Select
- Radio
- Date
- Table
- Modal
- Submit
- Validation
- API 初始化
- buildRequest
- error handling

则分别在标准仓库 A/B 中找最接近的真实页面和实现。

每个对比项至少记录：

| 项目 | 内容 |
|---|---|
| AI 项目文件 | 当前真实路径 |
| 标准仓库 A | 对应真实路径 |
| 标准仓库 B | 对应真实路径 |
| 场景 | 例如字段渲染 / Submit / API / Validation |
| A/B 是否一致 | 是 / 否 / 部分一致 |
| 可否作为标准 | 可以 / 需适配 / 不可直接复制 / 待确认 |

不要拿“不相关页面”强行作为标准样本。

---

## 六、第三阶段：逐文件治理

按照当前 journey 的真实调用链，从入口开始逐文件检查。

不要一次修改全部文件。

顺序建议：

1. 页面入口与 route
2. 页面文件职责
3. import 与依赖来源
4. 公共组件
5. 字段渲染
6. 状态初始化
7. validation
8. submit
9. buildRequest
10. API/service
11. response/error/loading
12. modal/table/pagination
13. config/constants/strings/utils
14. mock/stub/dev/sit
15. localchange
16. 命名、代码风格和局部格式

对每个文件逐段阅读，不允许只看文件名和目录结构。

---

## 七、逐段 / 逐行判断规则

对于每一个有意义的代码块，必须判断属于以下哪一类：

### A. 完全一致

当前 AI 项目已经符合成熟仓库真实模式。

处理：保留，不修改。

### B. 语义一致但写法偏离

业务结果相同，但实现方式与标准仓库不同。

例如：

- 多了一层 wrapper
- 组件 props 组织方式不同
- validation 写在页面内而标准仓库放独立文件
- request 在 component 中拼装而标准仓库使用 buildRequest
- error/loading 流程不同

处理：如果没有业务风险，则向标准仓库收敛。

### C. AI 自造实现

标准仓库没有对应抽象，当前实现明显是迁移过程中 AI 自己创造的结构。

处理：优先判断能否删除并直接使用标准仓库已有方式。

### D. 合理业务差异

由 market、journey、API 或真实需求决定。

处理：保留，并记录为什么不能对齐。

### E. 标准仓库之间存在冲突

A/B 两个标准仓库模式不一致。

处理：不猜，不强改。记录证据和待确认项。

### F. 疑似错误 / 风险

当前代码不仅不一致，而且可能导致业务、状态、API 或 validation 风险。

处理：单独标高优先级；先说明风险，再决定修改。

## 八、每个差异必须给证据

禁止输出：

> “这里不规范。”

必须输出到这种粒度：

```text
AI 项目：src/.../xxx.jsx，第 xx-xx 行
当前实现：页面内直接构造 request payload

标准仓库 A：src/.../buildrequest.js，第 xx-xx 行
标准仓库 B：src/.../buildrequest.js，第 xx-xx 行
共同模式：Submit 校验通过后调用独立 buildRequest 组装请求参数

差异类型：B - 语义一致但写法偏离
治理建议：将 payload 组装迁移回当前 journey 的 buildrequest.js
业务影响：无，保持 payload 字段和接口调用时机不变
```

如果工具不能稳定提供行号，至少必须提供：

- 文件路径
- 函数名 / 组件名
- 对应代码片段定位

---

## 九、治理优先级

按照以下优先级处理，不要先做表面格式：

### P0：调用链错误或潜在业务风险

- Submit 流程
- validation
- API 参数
- response
- loading/error
- 路由
- market/localchange

### P1：架构与职责偏离

- 文件职责
- API/service 层
- buildRequest
- 公共组件
- 页面状态组织
- 重复 wrapper / adapter

### P2：局部实现偏离

- props 组织
- hooks/utils
- constants/config
- 组件拆分方式

### P3：代码风格差异

- import 顺序
- 命名
- 空行
- 局部代码组织
- formatting

必须先 P0/P1，再 P2/P3。

## 十、修改策略

如果本次任务允许直接修改代码，则采用“小批次收敛”。

每一批只处理一个明确主题，例如：

- 第一批：公共组件接入
- 第二批：validation + Submit
- 第三批：buildRequest + API
- 第四批：error/loading
- 第五批：config/constants/utils

每批修改后：

1. 查看 diff
2. 确认没有夹带无关改动
3. 执行项目已有最小验证
4. 页面行为可验证时执行对应验证
5. 再进入下一批

禁止一次性重写整个 journey 后再验证。

---

## 十一、公共组件专项检查

当前 AI 项目中每一个自定义组件都要额外问一次：

> 标准仓库是否已经有公共组件或固定使用方式解决同一问题？

如果有：

- 优先使用标准公共组件
- 对齐 import 来源
- 对齐 props
- 对齐 validation/error 绑定
- 对齐 disabled/readOnly/defaultValue
- 对齐事件命名和回调方式

如果没有：

- 才允许保留当前自定义实现
- 并说明保留依据

---

## 十二、完整流程专项检查

以下流程不能只对比单文件，必须端到端追踪：

### 页面初始化

```text
route → page → init → API → response → state → component
```

### Submit

```text
button → handler → validation → buildRequest → API → success/error → UI
```

### 字段错误

```text
validation rule → validation execute → error state → field props → UI error
```

### API 错误

```text
API reject/error code → handler → loading reset → message/modal → page state
```

### market 差异

```text
core default → market localchange → final runtime behavior
```

每条链路都与两个标准仓库对应链路比较。

## 十三、输出：逐行差异治理表

先生成一份差异清单，再开始大规模修改。

建议输出到当前 AI 项目已有的治理/迁移报告目录；如果已有固定目录必须沿用，不要新建顶层目录。

报告至少包含：

# 1. 本次范围

- 当前 market
- 当前 journey
- AI 项目路径
- 标准仓库 A
- 标准仓库 B
- 扫描文件数量

# 2. 当前 journey 完整调用链

必须是真实代码链路。

# 3. 文件对应关系

```text
AI 文件 ↔ 标准 A 文件 ↔ 标准 B 文件
```

# 4. 逐项差异矩阵

至少包含：

| ID | AI 文件 | 代码位置 | 标准证据 A | 标准证据 B | 差异类型 | 优先级 | 是否修改 | 原因 |
|---|---|---|---|---|---|---|---|---|

# 5. AI 自造结构清单

单独列出所有疑似 AI 自造的：

- 文件
- wrapper
- component
- hook
- helper
- adapter
- utils
- API 层
- validation 层

并逐项判断：

- 删除
- 替换标准实现
- 合并
- 保留
- 待确认

# 6. 合理差异清单

防止为了追求一致而错误修改业务特例。

# 7. 待人工确认项

只保留真正无法从两个标准仓库判断的问题。

# 8. 本轮治理结果

记录：

- 修改了什么
- 删除了哪些 AI 自造结构
- 哪些调用链已收敛
- 哪些仍未收敛
- 验证结果

## 十四、完成标准

不能因为页面“看起来正常”就判定治理完成。

当前 journey 只有同时满足以下条件，才可以标记为“基本收敛”：

1. 页面功能保持正常。
2. 核心调用链与标准仓库模式一致。
3. 公共组件使用方式已对齐。
4. validation / Submit 流程已对齐。
5. buildRequest / API 流程已对齐。
6. loading / error / response 处理已对齐。
7. 文件职责与标准仓库接近。
8. 无明显可删除的 AI 自造中间层。
9. 剩余差异均能被解释为真实业务/market/journey/版本差异。
10. 每个保留偏差都有代码证据，而不是“AI 判断这样也可以”。

---

## 十五、最终执行口径

这次工作的本质不是：

> 再总结一次标准仓库规范。

而是：

> 让当前 AI 项目的真实代码逐步向标准仓库真实实现收敛。

始终坚持：

```text
标准仓库真实代码
        ↓
找到同类场景
        ↓
当前 AI 项目逐文件对比
        ↓
定位具体偏离
        ↓
判断合理差异 / AI 自造差异
        ↓
小批次修改
        ↓
验证
        ↓
继续下一项
```

不要用第三份更大的规范文档代替真实代码治理。
不要一次性重构整个项目。
不要让当前 AI 项目已有错误模式反过来成为新的“标准”。

最终目标是把一个 journey 治理成可作为后续迁移参考的 Golden Journey，再用同样方法逐个 journey 收敛。
